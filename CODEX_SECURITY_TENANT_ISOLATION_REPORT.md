## 2. Real issues found and fixed during this work

### 2.1 Pending migration caused upload 500

The first probe run failed check 11 with `status=500 {"success":false,"message":"Server error."}`. `storage/logs/laravel.log` showed:

```
SQLSTATE[HY000]: General error: 1 table documents has no column named storage_disk
... DocumentController.php(320): Document::create(...)
```

`php artisan migrate:status` identified one pending migration, `2026_11_17_000001_add_vault_scan_lifecycle`. Its `up()` is strictly additive (adds defaulted columns to `documents`, `media_files`, `document_versions` and creates `document_quarantines`); no drops or renames. It was applied with `php artisan migrate --force`, and `migrate:status` now reports zero pending. **No rollback was performed.**

### 2.2 Quarantine policy (not a bug)

After the migration, upload returned `201` but "A can download its own private document" failed with `423`. Root cause is intentional: local `MALWARE_SCAN_FAIL_CLOSED=false` with no scanner available means the upload is stored fail-open as `scan_status=skipped` and quarantined; `DocumentController::download()` deliberately returns `423` until a rescan produces a clean verdict — even for the owner. The probe assertion was wrong, not the application. It was updated to reflect the recorded `scan_status`:

- `scanned_clean` → owner download must be `200`;
- `skipped`/quarantined → owner download must be `423`.

Cross-tenant download must always be `404`/`403`. With this honest, environment-aware assertion the final run is 21/21.

### 2.3 Rate-limit isolation

The probe uses TEST-NET-3 addresses (`203.0.113.201` normal, `203.0.113.202` for the deliberate throttle). Twelve failed logins produce ten `422`s then `429`, proving the configured 10/min limiter without poisoning the shared `127.0.0.1` bucket used by the E2E suite.
